# Prompt 00: Import an Existing Specification (spec/ → Aegis)

**Use when:** a specification already exists as several documents under `spec/` (written by another model or by
people), and the repository should be brought under the Aegis process.  
**Target Model:** Frontier model with shell access (a different model than the one that wrote `spec/`, so the import
doubles as a first independent reading).  
**Runs:** two separate sessions. Between them: blind reviews by a third model and the human's baseline approval; between
step 4 and 5 additionally the test review and the human freeze.

**Principle: deterministic before judgement.** The model writes what only understanding can produce (requirements,
architecture, use cases, test plan, tests). Everything checkable is checked by Aegis, and everything derivable is
generated by Aegis:

| Concern | Deterministic tool |
|---|---|
| Every spec section mapped, every citation valid | `aegis spec check` (writes `doc/spec-coverage.md`) |
| Artifact structure, IDs, links, layers | `aegis trace`, `aegis gate --only architecture` |
| Spec or artifact changes after approval | `aegis baseline` (`UNREVIEWED` / `SUSPECT`, incl. `spec/` files) |
| Tests cannot be weakened | `aegis tests freeze` / `test_freeze` stage |
| Global rules and loop protocol for the weak model | `aegis instructions` |
| Self-contained work packets in layer order | `aegis tasks` (refuses without baseline and frozen tests) |

---

## Prompt — Run 1: Import (ends with STOP)

````text
ROLE
You are a Principal Systems Engineer working inside this repository with shell access. The product specification
lives in spec/ (several Markdown documents, written by someone else). Bring the repository under the Aegis process and
translate the specification into Aegis artifacts under doc/. You never write production code. Prefer Aegis commands
over your own judgement wherever a command exists; report what they print instead of paraphrasing.

GROUND RULES
- spec/ is immutable. Never edit it.
- Every REQ, ARCH and UC cites its origin in its metadata: source: [spec/<file>.md#<anchor>]. Anchors come only from
  `aegis spec sections` — never construct them yourself.
- Never invent requirements, numbers, roles, interfaces or limits. Where spec/ is silent, ambiguous or contradictory:
  aegis issue create --type question --severity <low|medium|high> --related <IDs> --title "..." --description "..."
  and continue; never resolve it by guessing.
- Branch aegis/import; commit after every numbered step; never push.
- Never modify tools/aegis. Never run `aegis baseline --approve` or `aegis tests freeze` (human decisions).

1. ADD AEGIS
1.1 git submodule add <AEGIS_GIT_URL> tools/aegis — skip if tools/aegis already exists
    (record the pinned commit: git -C tools/aegis rev-parse HEAD).
1.2 cargo build --release --manifest-path tools/aegis/Cargo.toml; alias aegis=tools/aegis/target/release/aegis.
1.3 Use the profile, overlays and project name the user gave you. Only if none were given, choose them from the
    specification — web-enterprise | enterprise | local-first | embedded-safety, for web-enterprise the frontend
    overlays none | rust-web-htmx | rust-web-pwa — and justify the choice in one paragraph. Then:
      aegis init --profile <profile> --lang <lang> [--name <project-name>]
    (profiles init does not scaffold, e.g. local-first: run init with --profile enterprise, then copy
    tools/aegis/doc/<profile>.yaml to doc/profile.yaml and every ruleset it lists from tools/aegis/doc/rules/ to
    doc/rules/). Enable the overlays under `rulesets:` in doc/profile.yaml. If a Cargo workspace existed before, add
    "tools/aegis" to its `exclude` list.
1.4 In doc/profile.yaml set gate.traceability.spec: required.
1.5 Read completely: tools/aegis/doc/dev-workflow.md, tools/aegis/doc/prompts/01, 03, 04, 04b and 08,
    doc/profile.yaml and every ruleset it lists.

2. TRANSLATE
2.1 aegis spec sections > /tmp/sections.txt — the complete list of citable sections. Read every file in spec/.
    Markdown files are cited per heading (spec/<file>.md#<anchor>); every other file (OpenAPI, JSON Schema,
    diagrams) is one citable unit (spec/<file>) and must be cited or excepted like a section.
2.2 doc/001_initial_spec.md: consolidated specification in the structure of Prompt 01 (all nine ISO/IEC 25010 axes as
    Required/Recommended/N/A with rationale; scope and explicit non-goals; open questions = the issues you created).
2.3 doc/requirements/REQ-<AREA>-NNN.md: atomic, testable, one obligation each; frontmatter id, title, status: draft,
    type, iso25010, source. Non-functional requirements need measurable thresholds — TBD plus an issue if spec/ has none.
2.4 doc/architecture/ARCH-xxx.md: one element per layer crate of the profile's gate.architecture policy (plus the
    cross-cutting components spec/ demands) with `crate: <project>-<layer>`, satisfies, source; responsibility, exact
    public interface (signatures, error variants), resource model, integration verification. `crate:` is mandatory —
    `aegis tasks` derives order and scope from it.
2.5 doc/usecases/UC-xxx.md: implements, audience (user | operator | none), source; main and edge flows.
2.6 doc/testplan/TEST-xxx.md: every REQ and every ARCH verified (verifies: [REQ-..] / [ARCH-..]); deterministic steps,
    expected results, edge and failure variations.
2.7 Where applicable: openapi/<project>-openapi.yaml (contract first) — if spec/ contains an OpenAPI document, copy
    it unchanged and cite it from the ARCH element of the api crate (source: [spec/<file>]); doc/privacy/
    data-inventory.yaml (TBD where unknown), doc/deliverables/manifest.md.
2.8 Sections that intentionally map to no artifact go into doc/spec-coverage.yaml:
      exceptions:
        - section: spec/<file>.md#<anchor>
          reason: <why it is out of scope>      # or
          issue: ISSUE-xxxx                     # still open
    Never add an exception to silence a section you simply did not translate.

3. VERIFY (fix and repeat until clean)
3.1 aegis spec check            -> "Specification fully covered." (no UNCOVERED, UNSOURCED, unresolved source)
3.2 aegis trace                 -> no INVALID, DUPLICATE, ORPHAN, EMPTY. Allowed now: GAPs for @implements/@verifies
                                   (no code yet) and undocumented use cases.
3.3 aegis baseline              -> dry run lists the artifacts; it must not refuse.
3.4 For a Rust workspace: cargo build && aegis gate --profile doc/profile.yaml --only build,architecture
3.5 Review skeletons for the blind reviewers, one per stage spec, requirements, architecture, usecases, testplan:
      aegis review create --stage <stage> --artifact <paths> --reviewer TBD --author <your model id>
3.6 STOP. Report verbatim: the output of 3.1–3.3, profile and overlays, counts (REQ/ARCH/UC/TEST), open issues by
    severity (aegis issue list). Do not continue until told "baseline approved".
````

---

## Between the Runs (human + reviewer models)

1. Blind reviews per stage (Prompt 02 template, recorded in the review skeletons), findings dispositioned, artifacts fixed.
2. `aegis review check --required spec requirements architecture:2 testplan` green.
3. `aegis baseline` (dry run) reviewed, then **`aegis baseline --approve <name>`**.

---

## Prompt — Run 2: Tests and Work Packets

````text
ROLE AND GROUND RULES: as in Run 1. Additionally: the baseline is approved — any change to doc/requirements,
architecture, usecases or testplan now makes the gate red (UNREVIEWED/SUSPECT). Do not change them; open an issue.

4. TESTS FIRST
4.1 aegis baseline must print "Baseline is current". If not, STOP and report.
4.2 Implement the test plan per tools/aegis/doc/prompts/04b_test_implementation.md: dedicated test files (never in a
    file with production code), `@verifies TEST-xxx` on every test function, minimal compiling stubs (// STUB) in the
    layer crates where code is missing.
4.3 cargo test: every test must fail against the stubs for the reason its TEST-xxx describes. Fix tests that pass.
4.4 aegis trace: no "specified in test plan but not implemented" GAPs left.
4.5 Review skeleton: aegis review create --stage testplan --artifact <test files> --reviewer TBD --author <you>.
4.6 STOP. Continue only after "tests frozen" (the human runs aegis tests freeze after the test review; it refuses
    unless the tests compile and every new test fails against the stubs).

5. WORK PACKETS (generated, not written)
5.1 aegis tests verify          -> all test files frozen and unchanged
5.2 aegis instructions --profile doc/profile.yaml --out AGENT_INSTRUCTIONS.md
5.3 aegis tasks --profile doc/profile.yaml
    It refuses without a current baseline or frozen tests, orders packets by layer, embeds requirement, use cases,
    architecture, the source of the frozen test functions, the stubs to fill in (todo!() / // STUB) with the type
    definitions they use, rules, gate command and escalation format. If it reports OVERSIZE or UNPLACED,
    do not edit the packets: open an issue proposing the split or the missing `crate:` (spec change -> review ->
    re-baseline -> regenerate).
5.4 aegis gate --profile doc/profile.yaml --only build,architecture,test_freeze -> green.
5.5 STOP. Report verbatim: the doc/tasks/README.md queue table and the output of 5.3–5.4.
````

---

## After Run 2

The implementation model works through `doc/tasks/README.md` in order (one packet per session or loop iteration,
[Prompt 06](06_27b_implementation.md)); the harness guardrails are listed at the end of the queue file. After the queue:
full gate (`--skip reviews`), final review (Prompt 07), acceptance gate. Re-run `aegis tasks` whenever the baseline
changes — packets are build output, not documents.
